# Better Recipe Book: Rebetterered crafting controller regressions

`CraftRequestChecksTest.java` executes the unchanged production sequence and ingredient-assignment helper. It passed 131,072 assertions covering all 15-bit sequence baselines, forward updates, duplicates, stale updates and ambiguous half-range distances. Six assignment regressions cover overlapping alternatives, repeated ingredient slots, malformed matrices and the full 3x3 bound.

The real Minecraft tests are in `ported/src/clientqa/java/marsh/town/brb/clientqa/CraftingChecks.java`. The root QA entrypoint calls `run(context, world, evidence)`. Those tests drive actual recipe buttons in both 2x2 inventory and 3x3 crafting-table screens, and verify server inventories after left-click, Shift-left-click, right-click and Shift-right-click. They also cover prepared local recipes without a new placement update, fresh local recipes from one-item and larger inventory sources with single and maximum crafting, manually prepared renamed ingredients, protection of valuable inventory items, unresolved required ingredients, crafting beyond the initial 64-batch grid fill, full inventories, occupied cursors, disabling instant craft, closing a pending menu, and rejected armor-slot storage. Their existence is not evidence of a successful gameplay run; consult the root QA output for executed results.

The crafting implementation sends vanilla recipe-placement and container-input packets. One batch uses a single result pickup followed by checked inventory storage. Maximum crafting repeats a batch only after a fresh server result update. A zero-click local placement can reuse an unchanged prepared result after exact output and grid validation. Automatic crafting/furnace inventory selection follows vanilla protection for renamed, damaged and enchanted items; manually prepared ingredients and component-preserving smithing inputs remain usable. It does not use quick-move for results, because a partial final batch can spill from vanilla quick-move behavior. It invalidates pending work on manual inventory interactions, ordinary recipe placement, failed placement ghost, unmatched full content resynchronization, timeout, changed screen/menu/connection, or disabled controls. Rapid requests while one is pending are safely refused.

The vanilla recipe-placement protocol has no client request nonce. The implementation combines the exact menu/screen/connection objects, a newer result-slot sequence, expected output count and components, and recipe-shaped ingredient-grid validation. Full content corrections continue maximum crafting only when their inventory, grid and cursor exactly match a captured state from the active placement or crafting batch. Intermediate placement and storage states wait for the final confirmation; unmatched corrections invalidate the operation. Smithing may suppress an empty result acknowledgement when prediction matched, so its next placement follows the successful pickup/storage in packet order and requires a fresh confirmed result before another craft. Unknown recipe displays are refused for automatic crafting. Dynamic modded recipe side effects beyond communicated displays and ordinary item crafting remainders require targeted compatibility tests.
