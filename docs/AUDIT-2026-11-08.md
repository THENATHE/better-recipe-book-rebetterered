## Vanilla++ and Tiered Backpacks integration

The two integrations point in both directions, so both sides were checked against current sources.

- **BRBR → backpack crafting.** `BackpackBulkCraftingMixin` targets `com.thenathe.backpackcrafting.menu.BackpackCraftingMenu` (mod ID `vpp_backpack_crafting`) and shadows `getStorageStart()`, `getInventoryStart()` and `getBackpack()`. All three are unchanged in Vanilla++ 1.4.5 and on the suite's in-progress `update/2026-11-upstream-audit` checkout. The holder update writes `DataComponents.CONTAINER`, which Tiered Backpacks 1.0.21 (`Fh8qqxFD`, `23bbe022…`) still uses for backpack contents. 1.0.21 replaces its crafting-menu upgrade mixin with a shaped-recipe mixin and adds a `canOpenFromInventory` option; neither changes the menu slots or container component BRBR reads.
- **Backpack crafting → BRBR.** Vanilla++'s `backpack_crafting_brbr.mixins.json` is `required` and targets BRBR internals: the two `instanceof CraftingMenu` checks in `InstantCraftingManager.requestCraft(...)`, static `isPlayerStorage(Minecraft, Slot)`, the third `Pending.receivedResult` read in `tick()`, the `Pending` fields `menu`, `resultSlot`, `maximum`, `matchesOutput` and `matchesGrid`, and static `WorkstationTransfer.isInventory(Slot)`. None of these changed. They are now checked on every build by `qa/tests/BackpackCraftingContractChecks.java`, so a refactor that would crash the suite at startup fails `gradlew check` first.

The full client run loads Vanilla++ 1.4.5 with the candidate, which applies both sets of mixins at startup. A follow-up retest used Vanilla++ 1.5.0+26.3 (source `db3eeac`), which bundles Tiered Backpacks 1.0.21 and backpack crafting 1.1.0. Its BRBR mixins are unchanged. The full client and all four connected backpack profiles passed with the unchanged 1.11.8 JAR (see VALIDATION).

## Findings fixed

1. **Unreadable settings were overwritten with defaults** (`BetterRecipeBook.java:31`, Cloth Config `ConfigManager.load`). When `config/brb.toml` could not be read, Cloth used defaults, and the next routine save replaced the file. BRBR saves often: every instant-craft toggle and every workstation open/close or Show craftable click. Cloth also writes the file in place, so a crash during a save could leave it truncated. The new `config/AtomicConfigSerializer.java` keeps Cloth's TOML format and file name. It saves through `brb.saving.toml` and an atomic move, and copies an unreadable file to `brb.toml.unreadable-<time>` before the first save replaces it, the same way `brb.pins` already works.
2. **Some unreadable settings files left the mod without registered settings** (`BetterRecipeBook.java:39`). Cloth only handles `IllegalStateException` from its TOML reader. A truncated file (wrapped `RuntimeException`) or a wrong value type (`JsonSyntaxException`) escaped `AutoConfig.register`. The settings then never registered, `configHolder` stayed null, the settings button and Mod Menu entry threw, and the instant-craft toggle hit a `NullPointerException` (`InstantCraftingManager.java:694`). The serializer now reports every read failure to Cloth as unreadable settings, and the toggle checks `configHolder` like the workstation code already did. This was reproduced on the exact 1.11.7 JAR and verified fixed on 1.11.8.
3. **An unknown option name loaded as null** (`config/Config.java`). For example, an edited `overflow = "SPILL"` made Craft all treat overflow as "allow drops", because only `STOP_BEFORE_DROP` stops spilling. `Config.validatePostLoad()` now restores the default for each unknown enum or missing section and keeps every other saved value. This was reproduced on 1.11.7 and fixed.
4. **Small per-frame allocation** (`mixins/pins/RecipeBookComponentMixin.java:59`). The Pinned Recipes tab built a new knowledge-book `ItemStack` every frame. It is now created once per tab, as the workstation tabs already do.
5. **QA launchers pointed at the user's display and at old dependency versions** (`qa/run_packaged_client.py`, `qa/run_remote_client.py`, `qa/backpack-layout/network.py`). They defaulted to `DISPLAY=:1` and had Loader 0.19.5, Fabric API 0.161.0 and gametest 6.0.7 hard-coded. They now require an explicit private `DISPLAY` (for example `xvfb-run`), clear `WAYLAND_DISPLAY`, and take `--loader`, `--fabric-api` and `--gametest-api` (defaults 0.20.1, 0.165.2+26.3 and 6.0.12+131f8d475d). The verified official 26.3 asset index that Mojang now serves (`331e5c80…`) is retained beside the earlier ones.

## Reviewed, not changed

- **Hard-coded English tooltips** in `workstation/WorkstationBookPanel.java` (`Left-click: place…`, `Expand N variants`). These would need new translation keys; presentation was left as it is.
- **`Ingredient.items()` deprecation** in `workstation/WorkstationRecipes.java:127` and `:132`. Vanilla 26.3 still uses and supports it, and there is no replacement for listing example stacks.
- **Mouse Wheelie compat** (`compat/mixins/mousewheelie/MixinMWClient.java`) targets a 1.20.4 API. It is preserved: the config is not required and only applies when Mouse Wheelie is installed, and no 26.3 Mouse Wheelie exists to test against.
- **Stale NeoForge TODO** in `compat/CompatMixinPlugin.java:28`. It is the original author's comment and harmless.
- **Threading.** `ClientRecipeRegistry.snapshot` runs on the integrated server thread. It only publishes volatile references and does its rebuild work on the client thread through `Minecraft.execute`. No change needed.
- **Pin identity cache.** It is cleared on every recipe-book rebuild (`mixins/ungroup/ClientRecipeBookMixin.java`), so repeated unlock-all toggles do not keep growing it.
- **Network payloads.** BRBR is client-only and adds no packets. Server authority over crafting stays vanilla's.

## Data compatibility

The settings file name, TOML keys and values are unchanged. Pins (`brb.pins`, version 2) and the pin key (`key_key.brb.pin` in `options.txt`) are untouched. The upgrade test saved non-default values for all 20 settings, five exact pins (three crafting variants, one smithing and one brewing workstation variant) and a rebound pin key with the real 1.11.7 JAR. The 1.11.8 JAR loaded every value unchanged, and the startup re-save wrote byte-identical settings. Downgrading to 1.11.7 reads the same files.
